## 本机交付位置

根目录：`.package/diagnostics-capability-fix-20261124/`。

- `signed/`：正式签名包、所有分卷、manifest、SPDX 与现有受信公钥。
- `release-assets/`：集中上传 Release 的文件，带 `SHA256SUMS.txt`。
- `catalog.generated.ts`：仅替换上述三项的候选能力目录，其他组件沿用当前目录。
- `preparation.json`：可信源归档与文件核对记录、更新的脚本摘要。
- `release-inventory.json`：最终文件大小、SHA-256、制包校验范围及发布状态。

原始归档首先依据当前受信签名目录核对签名、大小和 SHA-256；提取后的保留文件逐项核对。源码目录中的缓存不进入新包，Worker 与必要本地辅助模块取自当前源码。新包再核对签名、归档摘要、SPDX 摘要及依赖目录的一致性；这些属于制包完整性校验，不代表运行或画质验收。

## 发布及使用顺序

1. 将 `release-assets/` 下所有 `.tar.gz`、`.manifest.json`、`.spdx.json` 上传到现有 `components-v1` Release。克隆 CPU 的三个归档和 CUDA 的四个归档必须全部上传，视频基础包一个归档；不能只上传主包。
2. 文件可用后，将候选目录接入主程序构建。候选目录不是已发布声明，本轮不提前改写实际内置目录，不让现有客户端请求尚未上传的新地址。
3. 桌面程序需包含统一禁写字节码及独立缓存前缀修复。完全退出旧进程，安装更新后的桌面程序，再通过能力管理安装匹配版本的新包。
4. 克隆先更新 CPU 基础包，使用 NVIDIA 加速时再更新 CUDA 扩展。视频更新基础包；已有 `video-ai-cuda@1.1.0-py312-cu1241` 的锁定资源可继续按现有协议使用，本轮不重复制作或下载该扩展。
5. 由用户运行实际功能及深检验收。旧签名包中已经变化的 `.pyc` 仍会如实报告，不通过忽略摘要、手改 current 或覆盖模型来消除提示。
